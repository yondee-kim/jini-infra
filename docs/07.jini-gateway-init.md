## jini-gateway 프로젝트 초기 생성

### 배경
auth·chat 서비스 분리를 마친 뒤, 브라우저의 단일 진입점 역할을 할 API Gateway를
세운다. jini-gateway는 8080 포트로 뜨며, 이후 단계에서 /auth·/chat 경로를 각
서비스로 라우팅하고 정적 화면도 게이트웨이를 통해 서빙한다. 이 단계(D-1)는
라우팅 로직 없이 프로젝트 뼈대와 빌드·CI 구성까지만 다룬다.

게이트웨이를 먼저 세우는 이유: 화면(login/list/room/stream)을 서비스별로 쪼개면
브라우저 localStorage가 출처(origin=프로토콜+호스트+포트)별로 격리돼 auth(8081)에서
저장한 JWT를 chat(8082) 화면이 못 읽는다. 게이트웨이로 단일 출처(8080)를 만들면
이 문제가 사라지므로, 화면 분리(C)보다 게이트웨이(D)를 먼저 진행한다.

### 스택 선택
- Spring Cloud Gateway는 4.1.x부터 두 종류가 있다.
  - Server WebFlux: 리액티브(논블로킹) 프록시. MSA 표준.
  - Server WebMVC: 서블릿 기반. auth·chat과 동일 스택.
- WebFlux를 선택했다. 게이트웨이는 다운스트림과 스택이 같을 필요가 없고,
  리액티브 프록시가 실무 표준이며, 이후 chat 스트리밍(SSE) 프록시도 WebFlux에서
  더 자연스럽게 흐른다. auth·chat이 MVC인 것과 무관하게 게이트웨이만 WebFlux로 간다.

### 버전 호환
- Spring Boot 4.1.0에 맞는 Spring Cloud 릴리스 트레인은 2025.1.2 (Oakwood).
  이 트레인이 Spring Boot 4.1.0 호환성을 도입했고, gateway 등 각 모듈은 5.0.x다.
- build.gradle: 플러그인 org.springframework.boot 4.1.0 +
  io.spring.dependency-management 1.1.7, BOM은
  org.springframework.cloud:spring-cloud-dependencies:2025.1.2.
  공식 Spring Cloud 시작 가이드의 Gradle 예시와 동일한 조합.

### 프로젝트 설정
- 재활용: jini-auth의 gradle wrapper(9.5.1), .gitignore, .gitattributes.
  그 외 모든 파일은 게이트웨이용으로 새로 작성.
- build.gradle 의존성:
  - spring-cloud-starter-gateway-server-webflux (핵심)
  - spring-boot-starter-actuator (health/info 확인용)
  - spring-boot-devtools, starter-test, reactor-test
  - auth·chat과 달리 JPA·postgresql·security·JJWT·springdoc은 전부 없다.
    게이트웨이는 프록시만 하고 DB·인증·엔티티를 갖지 않는다.
- settings.gradle: rootProject.name = 'jini-gateway'
- JiniGatewayApplication: com.jini.gateway 패키지, 순수 @SpringBootApplication.
- application.yml: server.port 8080, management.endpoints.web.exposure
  health,info. 라우팅 규칙(spring.cloud.gateway.*)은 비워둠 — D-2에서 추가.
- JiniGatewayApplicationTests: contextLoads만.

### CI
- .github/workflows/ci.yml: auth·chat CI에서 postgres service 블록과 DB/JWT/OAuth2
  env를 전부 제거하고 순수 ./gradlew build만 수행.
  게이트웨이는 외부 의존이 없어 컨텍스트 기동에 어떤 env도 필요 없다.

### 확인
- 버전 조합(Boot 4.1.0 + Spring Cloud 2025.1.2 + gateway-server-webflux)은
  공식 문서로 교차 확인.
- 로컬 ./gradlew build 통과 확인은 별도로 수행 필요.

### 남은 작업
- D-2: 라우팅 규칙. auth·chat의 실제 엔드포인트 경로를 확인해 predicate 설계
  (/auth/**, /oauth2/**, /login/** → auth / /chat/**, /conversations/** → chat).
- D-3: 인증 위치. 게이트웨이는 프록시만, JWT 검증은 각 서비스가 계속 담당.
- D-4: 정적 화면 단일 출처 서빙 + OAuth2 redirect-uri 재정리.
